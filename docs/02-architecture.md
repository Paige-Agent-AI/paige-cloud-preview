## Ecosystem service integration

Cloud owns the control plane for registration, authorization at Cloud boundaries, resource provisioning, builds, deployment, health evidence and governed execution. Each product keeps its canonical repository, application and environment identities, business logic, data grants and independent release lifecycle. Each shared capability stays with its original source owner. A product can run on PAIGE Cloud from its own reviewed repository or consume a versioned capability hosted under the original owner's authority.

| Interface | Contract and ownership |
| --- | --- |
| API | Publish versioned operation IDs, request and response schemas, errors, authorization requirements, deprecation policy and acceptance evidence. The owner of each service maintains its contract. The server checks authority on every request. |
| SDK | Publish versioned clients when a supported API and compatibility matrix exist. Reuse the API's scopes, retry and idempotency behavior. |
| CLI | Reuse the same service decisions, operation IDs and output schemas. Keep the qualified operator tooling separate from ordinary project access. |
| MCP | The original MCP gateway discovers approved capabilities and invokes the same versioned operations under Trust and Spine. Recheck scope, approval and quota at dispatch. |
| CI/CD | Resolve the stable repository ID, allowed protected ref and exact reviewed commit through the existing connection. Separate source and build identities from deploy and runtime identities. Accept an immutable artifact, promote independently, verify serving health and retain recovery evidence. |
| Events and webhooks | Route versioned asynchronous contracts through Action Bus. Qualify subscriptions, delivery authentication, event identity, idempotency, replay and dead-letter handling per scope. Use Rail for durable evidence and correlate asynchronous usage to the action. |

Workload identities are distinct per application and environment. Service accounts use short-lived credentials with a specific audience, operation scope and revocation policy. Qualify tenant and environment boundaries, permissions and entitlements, quotas, actor and operation cost attribution, secret rotation through Vault, and recovery independent of the delivery client. Trust and Spine decide and classify authority. Work, Harness and Orchestration own durable execution. Action Bus coordinates events, Rail preserves evidence, Model Fabric retains routing authority, and Intelligence/Evals evaluates verified outcomes. The SDK, CLI, MCP and webhook adapters use those same decisions and receipts.

Keep serving artifacts, runtime configuration pins and recoverable data in the relevant AWS resource scope. An already deployed workload should serve or recover during Mission Control or GitHub outages when its actual runtime dependencies are healthy. Verify that behavior with source and control-plane outage tests and a scoped recovery exercise. Use a versioned library when callers can upgrade it safely with their release and it needs no independent state, privilege or availability. Host a service when it needs independently managed data, privileged access, scaling, isolation or lifecycle. Compare measured latency, blast radius, compatibility, backup and gross cost before extracting a service.

Mission Control's Developer Platform starts with API reference and capability discovery for the signed-in account. As each interface qualifies, connect SDK/CLI releases, governed MCP discovery, service accounts, event/webhook subscriptions and usage evidence to the same application and environment scope. Keep deployment and recovery controls in their existing operating views. [Private Developer Platform contract](../infra/aws/customer-zero/README.md#developer-platform-reference)

Use the existing repository-to-deployment work as the first Cloud control-plane integration. The published inventory and serving alias are qualified privately, while protected source retrieval and governed promotion still need runtime proof. Ask PAIGE is the first product integration case for a hosted web experience with scoped identity, one persisted record, exact release evidence and independent recovery. Its product lead supplies the reviewed source and runtime contract, while Cloud provides infrastructure; signed-in Cloud browser sessions do not become product service credentials. ## Independent database-contract baseline

The original PAIGE Agent AI database-contract job replays migrations and reproduces deployed API-role object ACLs and PostgreSQL default privileges before applying candidate migrations. Use a restricted schema-only baseline with a known deployed source commit. Preserve the original full schema, custom roles, explicit public ACL dump, raw pre/post migration lists and normalized recorded versions. Retain the exact PostgreSQL image digest and CLI version. A migration replay alone cannot reconstruct observed deployed grants.

Before admitting a baseline to CI, restore it in isolation. Reconcile the recorded migration frontier against the original source, compare roles, object and default ACLs, ownership, extension versions, RLS, and privileged function behavior. Use the original grant reconciler and run the complete unmodified database-contract suite, including the candidate migration ordering proof. Keep exports in restricted custody and file independent capture and restore evidence in the existing record. [ANT-178](https://linear.app/paigeagentai/issue/ANT-178)

The portable gate reads `manifest.json` and the six original files. The manifest uses schema `paige.database-baseline.v1` and carries `sourceCommit`, `capturedAt`, `postgresVersion`, `cliVersion`, `postgresImage` (the image digest), `captureReceipt`, `restoreReceipt` and a SHA-256 `files` map. Pin the manifest digest and source commit from the independently reviewed record outside the bundle.

```sh
node infra/aws/customer-zero/verify-database-baseline.mjs <local-bundle-directory> <approved-manifest-sha256> <deployed-source-commit>
```

This gate checks provenance fields and content integrity. Database verification requires the independently captured and restored bundle and the original suite.

## Historical F2 preview architecture

The private Cloud repository identifies the public frontend by full commit SHA. GitHub Actions builds and tests a static nginx image from locked dependencies and digest-pinned bases, then publishes the candidate to the private GHCR package. The job records both Git revisions and the image manifest digest.

An authorized operator promotes the digest to the dedicated Docker Image app in the existing Coolify Cloud project. Coolify manages the existing Traefik TLS proxy and the application on the Hostinger KVM 2. It pulls each release by digest. The public browser connects to the HTTPS preview, and Traefik routes to nginx on port 8080.

The governed preview serves no backend or auth endpoints. The build configuration substitutes a reserved invalid backend and the runtime limits browser connections to the preview origin. See [preview security](03-security-design.md) and the [release and rollback runbook](05-rollback-runbook.md).

The legacy Dockerfile previews stay on their recorded URLs. The F2 app uses its own stable origin for the entire deployment and rollback sequence.
