It creates the initial organization and membership together. The runtime database login can call scoped functions without access to the underlying tables. ## Private registry contract

Migration `002-registry.sql` is additive. The operator bootstrap applies it through the existing migration lock and checksum ledger after validating `001`. Run bootstrap twice to verify replay. Older Lambda versions can continue to serve account flows with the additive tables present. Roll back the application artifact to its earlier immutable version if needed. Keep the registry data for forward recovery.

Use an existing verified evaluator session through the private origin. Writes require that origin and JSON. The server derives the actor from the session, then PostgreSQL checks current membership and project grants. Service credentials and public enrollment require separate qualification.

| Method and path | Scope, request and result |
| --- | --- |
| `PATCH /api/cloud/auth/organizations/{organization}` | An active organization owner can submit `expectedName` and `name` to change the existing organization's display name. The organization ID and relationships stay stable. Same-name retries are safe. A stale name returns 409. |
| `GET /api/cloud/v1/organizations/{organization}/projects` | An active organization member reads only their explicitly granted projects. Returns IDs, names and project roles. A new organization can return an empty list. |
| `POST /api/cloud/v1/organizations/{organization}/projects` | An organization owner submits `id` and `name`. Creates one project and its creator’s project-owner grant together. Same request returns the existing record. |
| `GET /api/cloud/v1/organizations/{organization}/projects/{project}/applications` | An active project grantee reads the scoped application and environment registrations. |
| `POST /api/cloud/v1/organizations/{organization}/projects/{project}/applications` | A project owner submits `id`, `name`, `kind` (`application` or `service`), `environment` and optional `sourceRepository` (`owner/repository`). Reuse the same application identity and metadata to attach another environment. Returns the application and its environment IDs. |

IDs accept 1–48 lowercase ASCII letters, digits or hyphens, starting with an alphanumeric character. Names accept 1–120 characters. Registry limits are 50 projects per organization, with 100 applications and 50 environments per project. Success is HTTP 200. Bad fields return 400, a missing session returns 401, denied browser origin returns 403, an inaccessible target returns 404, and conflicting metadata or capacity returns 409. Responses are not cached.

Repository coordinates are desired source metadata. Registration does not fetch source, deploy anything, allocate compute, or read provider credentials. Resolve actual source and publish immutable artifacts as separate, independently authorized steps. The operator workbook should consume this contract after the authenticated navigation is approved.

### Private workload configuration

The configuration API uses the existing same-origin, verified Cloud account session and the exact registered organization, project, application and environment. A currently granted project member can read. An active project owner can write. The server derives the account identity from the session. The `005-workload-configuration.sql` migration creates immutable revisions with a restricted function-only runtime boundary and records the submitting account and save time.

Use `/api/cloud/v1/organizations/{organization}/projects/{project}/applications/{application}/environments/{environment}/configuration`.

| Method | Behavior |
| --- | --- |
| `GET` | Reads the latest saved revision or returns `{"revision":0,"configuration":null}` for an eligible empty target. |
| `GET /revisions/{revision}` | Reads a specific saved revision, including revisions above 32. |
| `PUT` | Saves the complete configuration with a matching `expectedRevision`. A same-value write at the current revision or a same-value retry of the immediately preceding revision returns the existing record. A stale conflicting write returns `409 configuration_changed`. |

A write submits exactly `expectedRevision` (0 for an empty target), `logLevel` (`error`, `warn`, or `info`), and `requestTimeoutMs` (an integer 100–30000). These are pilot settings for the versioned v1 schema. Credentials, freeform values and arbitrary provider parameters are outside the contract. Denial of a registered scope and absence of a target or historical revision return the same 404.

`006-configuration-history.sql` preserves the original revisions and admits one new immutable revision per registered environment per minute. No-op reads of the current revision and idempotent repeats of a committed save remain available during the interval. A stale conflicting change returns 409; a new change arriving too quickly returns `429 configuration_rate_limited`. The positive PostgreSQL integer range replaces the pilot limit of 32. Use a new revision with the prior values to restore desired configuration. Restore the actual runtime independently using the last verified published version and settings pin.

Apply 006 before promoting the v2 account package. The old write entry point still returns errors understood by the old package, and an old handler cannot write beyond the original revision range. Once a target passes revision 32, retain a compatible account artifact for recovery of its configuration control plane. The workload alias can still recover separately to its prior accepted version.

Keep the evaluator's complete revision history and all object versions pinned by a live or accepted recovery release. Retain the exact scope, saved revision, timestamp and digest when archiving. Never recycle a prior revision or silently apply a different one when the requested revision is unavailable. A commercial retention policy needs an attributable storage budget and a verified archive and restore procedure before any deletion of historical rows or pinned copies is enabled.
